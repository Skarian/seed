# Operational details

## Package shape

The skill is the user-facing agent entry point, while the web app remains normal application code in the same repository. The agent can install/build that app and operate its worker; it does not need the React source copied into its skill instructions. Keep one repository and private local credentials, without another provider orchestration service. This first implementation expects an existing checkout; fetching the app from GitHub or an npm release is a later installer improvement, not an implemented command.

## Dependencies and state

`doctor` is read-only. The host needs Node compatible with the checkout's package.json (currently 26.8.2 through 26.x), OpenSSH client (`ssh`, `ssh-keygen`), installed npm dependencies and `npm run build`. No PowerShell, Docker, local Python, Vast Python SDK or AWS tooling is needed to launch the published image. Use the appropriate official Node installer/package for Windows, macOS or Linux. OpenSSH Client is a Windows optional capability, ships with macOS, and is normally available through Linux's package manager (`openssh-client` on Debian/Ubuntu). Agent installation must respect the user's system-change permissions. Run `npm ci` and `npm run build` in the checkout when needed. A system Node upgrade is not part of every launch.

The helper keeps non-secret per-checkout state under the Git-ignored `.local/seed-vast/` directory. `vastApiKey` lives in Seed's existing per-user `credentials.json`; worker secrets, SSH keys, connection backups and logs live in its `seed-vast/` subdirectory. Paths come from Seed's storage module, so they follow platform conventions. Files are private JSON (not application-encrypted): POSIX directories/files are created with 0700/0600 modes, and Windows uses the user's config-directory ACLs, matching Seed's existing credential convention. OpenSSH creates its private key with its own protections. VAST_API_KEY, HF_TOKEN and CIVITAI_API_TOKEN can override saved credentials. `setup` delegates to `seed setup --provider vast` (including HF, optional Civitai and Windows startup), then performs a read-only Vast authentication check. Stop the local app before setup; start it afterward. Tokens never go into command arguments or output, and writes preserve other saved credentials. Do not route secrets through an agent's text-question widget.

The old trial's DPAPI Vast key was migrated once on the development PC; the maintained skill has no PowerShell/DPAPI dependency. Other users use the shared setup flow or environment variables. Old encrypted trial files are not silently decrypted by the portable CLI. If an earlier skill version has a retained live instance, finish that session before changing launchers; the new SSH key and tunnel paths are different.

The helper's API operations use the live-verified routes: `GET /api/v0/users/current/`, `POST /api/v0/bundles/`, `GET /api/v1/instances/`, `PUT /api/v0/asks/{offer}/`, per-instance `GET/PUT/DELETE /api/v0/instances/{id}/`, and `POST /api/v0/instances/{id}/ssh/`. Preserve trailing slashes: a redirect previously dropped authentication. Offer searches use machine_id/gpu filters rather than an unsupported ask-id filter, then match the returned id locally.

Official references: [Vast CLI](https://github.com/vast-ai/vast-cli), [SSH launch mode](https://docs.vast.ai/guides/instances/connect/overview), [data movement](https://docs.vast.ai/guides/instances/storage/data-movement), [instance management](https://docs.vast.ai/guides/instances/manage-instances). If the API changes, inspect the official client before inventing a replacement request. Provisioning a new instance is not an authentication diagnostic.

## Compatibility boundary

This skill initially pins the exact Seed image used in the successful September 10 trial. Vast uses SSH launch mode, which overrides the image command. `boot` copies a small launcher to the instance, generates fresh pairing/Jupyter credentials and starts the worker. The launcher makes narrow, checked substitutions to that image's worker entrypoint: loopback transport is allowed only with the existing development flag, and worker/Jupyter listen on loopback. It uses `/` as the mounted workspace for the disposable container disk. This is an explicit compatibility bridge, not a new public HTTP endpoint or a general-purpose code patcher. An incompatible entrypoint fails before launching.

The helper forwards local 18080/18888 to the remote loopback services. `connect` uses a managed local launcher with Seed's existing `localTestWorkerOrigin` option. A small Node supervisor owns SSH and reuses Seed's authenticated loopback lifecycle protocol for shutdown, avoiding OS-specific process inspection and PID reuse. Commands use argument arrays with no local shell. It preserves the old connection and restores the ordinary app on teardown or failed pairing. The tunnel and trial launcher aren't sign-in services; after a PC restart, rerun `connect` with the retained instance running. A stopped instance must be started explicitly through Vast before `boot/connect`; GPU availability on that host is not guaranteed.

This keeps today's skill compatible without rebuilding the image or changing Seed's production endpoint validation. If this becomes the normal deployment path, replace the compatibility substitutions and test launcher with explicit, tested SSH-transport settings in Seed. Don't silently broaden the public endpoint allowlist.

## Baseline and validation status

The manual predecessor was live-validated on one RTX PRO 6000 WS in South Korea: all 99.62 GB/11 base-model files downloaded and verified in 314.79 seconds; 15-second mixed-reference video executed in 803.237 seconds at 63.33 GiB NVIDIA peak; a following image job took 12.284 seconds. Total provider charge was approximately $0.656, including GPU, disk and bandwidth. This is historical evidence, not a promise of price, speed or stock.

The reusable helper should be checked with `doctor`, `offers`, `billing` and `node --test <skill>/scripts/seed-vast.test.mjs` before use. Those read-only/offline checks do not validate a new full paid lifecycle. The next authorized live launch must verify provision → SSH → preparation → pairing → generation → safe teardown and document any differences. Never claim this refactoring has had a fresh live GPU test until that has happened.

The cross-platform rewrite passed 12 Node tests on Windows and in a local Linux container (`node:26.8.2-alpine`, repository read-only, container network disabled). Live read-only setup, offers, status and billing also passed on Windows. The tests cover shutdown identity and freshness, price checks, uncertain-rental recovery, literal process arguments, private state and occupied ports. Python tests for the unchanged GPU entrypoint adapter run from the checkout (or set `SEED_REPO`). macOS execution and the full paid lifecycle of this rewrite remain unvalidated; portable APIs and offline tests are not evidence of a completed GPU launch. Docker was used only as a Linux test environment, not as a runtime dependency. No GPU was rented to validate this refactoring. A discoverable copy is installed under the user's Codex skills folder; the repository copy is the versioned source.
