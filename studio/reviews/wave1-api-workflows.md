# Wave 1 — API, assets and workflow readiness

9 September 2026. Independent planning review; no runtime changes or paid tests.

**Planning readiness: 82/100.** The four-workflow product and single backend are sound. The main gaps are concrete timing semantics, undefined request fields, and unnecessary custom transport/state machinery. These are resolvable before implementation; live model quality remains an acceptance gate, not something a document establishes.

## Critical / major findings

1. **Last-frame anchoring conflicts with exact-duration trimming.** Native FL2VA puts `last_frame` at `frame_count - 1`. Five-second generation has 124 frames, while export keeps 120; native ending index 123 disappears. Ten and fifteen seconds have the same class of issue. For last-frame requests, use a native AddGuide candidate at **exported frame index `round(seconds * 24) - 1`**, not the generated final frame. For 5/10/15 seconds, test 119/239/359. Feed the correct latent and preserve prompt conditioning; do not also bind a contradictory native final frame. AddGuide accepts arbitrary frame indices, but temporal encoding may make influence approximate: test the exported final frame and nearby frames, not merely successful node execution. If quality fails, implement an explicitly tested endpoint-preserving finishing policy; do not claim an exact matching endpoint or hide failure. Source: [native H3 code](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy_extras/nodes_minimax_h3.py).

2. **Reference-video effective ranges remain underspecified.** Native Ref2VA first caps video frames to generated length and then rounds down to 17k+5. A 15-second reference with a 5-second output is not fully consumed. Compute and display the effective selected range before upload/generation; align paired audio to that same range. Document selected seconds, effective conditioning seconds and exported seconds separately. The client capability rules must include this route-specific requirement, beyond the official aggregate 15-second budgets. Do not promise every official maximum combination fits the current GPU.

3. **API request semantics are prose without an executable shape.** `prompt` is mandatory, but `prompt_fields` is said to be mutually exclusive. `audio.output=source` lacks concrete fields and behavior if the source is shorter than output; guide timing and image framing fields are unnamed. Define these now and add examples for first+last, image+video+audio, soundtrack replacement and two-image identity editing. Simplest option: one plain prompt string, ordinary optional Advanced controls, `audio: {output:'source', asset_id, start_seconds}` with an exact output-length segment required locally. Explicit `framing: 'fit'|'fill'` for anchors; no new rich-text document format.

4. **Do not invent a resumable-upload protocol.** Replace custom complete/status/offset machinery with [tus server and disk store](https://github.com/tus/tus-node-server) plus [tus-js-client](https://github.com/tus/tus-js-client). Mount inside the existing HTTP process; no sidecar or cloud upload service. A completion hook verifies/promotes the asset, and ordinary asset metadata reports verification readiness. Retain chunking, disk availability, partial cleanup and no arbitrary asset cap. tus already provides offsets, retries, expiration and termination. Avoid a redundant second uploads table if tus metadata plus an asset row is sufficient.

5. **Client metadata inspection must not be confused with playback or full corruption verification.** Browser metadata elements can fail on a file that the server FFmpeg could prepare, or succeed before late corruption. Use native previews plus a lazy local metadata probe such as [mediainfo.js](https://github.com/buzz/mediainfo.js), which reads slices without full-file video decode. The local result establishes supported codecs/streams and structural requirements, not proof of full-file integrity. HEIC fallback is bounded codec work, not a generic arbitrary-file transcoder project. Keep automatic conversion on the server for files admitted locally; reject unsupported files locally. Make client-versus-integrity test expectations precise.

6. **Cancellation has a manual-work race.** A check-current-then-global-interrupt sequence can interrupt a different manual prompt if the first job finishes between requests. For v1, designate ComfyUI queue as studio-owned during normal use and make direct manual generation an explicit maintenance session with dispatcher paused. If retaining concurrent manual generation, do not promise targeted running cancellation unless the pinned API offers it. Queued cancellation by prompt ID is fine.

7. **Seed transport needs a concrete choice.** A decimal uint64 string at the public boundary is correct, but converting through JS Number loses precision before ComfyUI JSON dispatch. Either use a tested integer-preserving JSON serializer for the graph or explicitly advertise the exactly representable range. Keep the string in persisted request/provenance. Add a round-trip fixture near 2^64-1 if claiming full uint64 support.

## Removals that reduce implementation risk

- Remove persisted SSE events/replay and the events table. Poll studio and active job snapshots every 2 seconds while active, slower/paused while inactive. Keep ComfyUI WebSocket only inside the adapter if useful.
- Remove server draft endpoints, draft conflict revisions and drafts table. localStorage per workflow is sufficient; Library/settings reuse supplies persisted cross-device results. State that unfinished drafts are device-local.
- Collapse generic operations resource into the single studio snapshot and start/stop responses; cancellation can be a studio action. Persist the current service operation internally without building an operations framework.
- Do not build a general form renderer or arbitrary graph compiler. Four React forms, common media tray, four small adapters, a handful of trusted graph templates, and short LoRA/reference-chain builders suffice.
- Do not build synchronized API and ComfyUI App exporters now. Preserve baseline editable graphs, maintain trusted API templates, and defer new App exports. Current user-facing product is the new frontend.
- Remove default rich reference-token editor and structured-prompt serializer. A textarea with insertable label buttons and a small label-remapping/validation utility supports native prompts without an editor framework. Test deletion/reordering so labels never silently refer to different inputs.
- Do not add a custom pod file endpoint first. Current upstream `/upload/image` accepts a generic multipart file despite its name; test MP4/WAV on the pinned server with generated filenames. Its implementation buffers file reads, so use only bounded prepared derivatives, with output transfer streaming. A custom streaming path is a measured fallback, not initial scope. [ComfyUI server](https://github.com/Comfy-Org/ComfyUI/blob/master/server.py).

## Lean module shape

`shared/` defines capabilities, request schema and pure checks. `web/` has four forms and shared status/media/library components. `server/http` handles auth and routes; `server/assets` wraps tus, ffprobe/FFmpeg and disk; `server/jobs` owns one durable queue; `server/comfy` compiles/submits/observes known templates; `server/lifecycle` handles the one Runpod service. SQLite stores assets, jobs and one service state; configuration files hold presets. Add tables only when a real persisted relation requires them. No extra worker service, message broker, plugin system, workflow DSL or generated admin console.

## Gate for a >=95 planning assessment

Apply the reductions; fix last-frame and effective-reference timing; finalize named request fields/examples, integer serialization and cancellation ownership. Keep mixed guides, HEIC behavior and maximum-reference quality as explicit bounded live checks with non-silent fallback. Then a second independent review can reasonably assess >=95 execution readiness without claiming 95% model success.
